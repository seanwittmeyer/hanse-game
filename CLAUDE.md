## Deploy — READ THIS: the user can only see work that is on `main`
- **The user plays/reviews the LIVE GitHub Pages site, which is served from the `main` branch only.** Anything that is merely committed to the feature branch — or just edited in the working tree — is **invisible to the user.** "Pushed" is not enough; it must be on `main`.
- **Therefore: after ANY change the user needs to see or test, publish it to `main` in the same turn.** The flow is always: commit on the feature branch → `git push -u origin <branch>` → **fast-forward `main`** (`git push origin <branch>:main`). Do not end a turn with user-visible work stranded on the feature branch. If you're unsure whether to publish, publish.
- The site is published from `main` via GitHub Pages (a `deploy-pages.yml` workflow with retries owns the deployment since 2026-07-06). After a push to `main`, GitHub Pages takes ~1–2 min to rebuild, and the user must **hard-refresh** (Cmd/Ctrl+Shift+R) to beat the CDN/browser cache. A save-`KEY` bump also clears any in-progress game (expected after a rules change).
- **This is a tabletop board game, not a web app.** Design for PRINT: if information isn't printed on a physical component, the player doesn't have it. **The component-state hard line (ruled 2026-07-12): ALL game state must be carried by physical components** — no rule may require memory, a ledger, or app-side tracking; if no component can hold it, the mechanic is out. `play.html` is the mirror, never a crutch. Tooltips/hover are a design smell — they flag info with no home on a piece. In `play.html`, essential info is shown INLINE because it is printed on the tile; tooltips may carry only flavor/reminders. Every change must work as cardboard, not just on screen.

## Working on this game — read this first
**A change is never local.** This is a tightly-coupled euro game: theme, mechanics, components, and the published pages all reinforce each other. Before touching anything, build the whole picture — a tweak to one number or rule ripples through scoring balance, the theme's logic, the component counts, and several docs. If you can't explain how a change affects each axis below, you don't understand it yet.

### The spine (internalize this — everything hangs off it)
- **The Wharf = four stations ringed by 8 slots; move where the board is best (NOT a rondel).** A turn = move to an adjacent station, activate its **row or column**, resolve the stops **in any order, all optional**: the two stations (ONE printed action each — Market Source 2 · Brewhouse Brew · Cellar Age 3 · Harbor Commission at the hull's printed fee: 2/1/0 G by size, v4.8) + each slot's **building action** and/or a **LOAD of the ship** docked there. Sharing a station costs **nothing** (v4.3 — the occupancy toll is CUT).
- **THE DIE IS THE CASK — the whole game in one component.** Brew sets a tray die to the printed start value (quality − aging steps); aging turns it up to the quality (READY) — **and it NEVER turns on its own (v4.5b)**: Cellar 3 · Mission Quay · Age bonuses · Assay · Racking · Hop Exchange · Abbey Cellar · Cellarman · Braumeister are the only hands; building lifts push past it (cap 6); gates read it as it boards; delivery parks it at the kontor as banked ★ (the pips), presence, majority weight and the end clock. No die in the tray → no brew, no build (v4.9), no presence bump. 13 dice (v4.9b) = the player's whole runway, public.
- **Slots hold a building and/or a ship — never casks.** Casks are PRIVATE until they board; the interaction is the **berth race** (topping off a hull sails everyone's cargo on your clock), the shared building actions, the ship-market draft and the majorities.
- **One green building family — and (v4.5b) the deck leans on the DIE.** Every building serves whoever activates it; building one **stands a tray die on it at face 1 (v4.9 — every use +1, cap 6, pips at end)**; earned (London/bonuses), never bought; overbuild = ONE payment (a paid fee covers the ground; 1 G rent only when otherwise free), displaced tile boxed — its die scores at once and returns. **The box prints 20 — setup deals 17 (v4.6; ≥1 Kiln + ≥1 MQ guaranteed).** 9 die-touching designs on a GWT-style cheap-utility→costly-power ladder, fees in grain only (v45d: Racking any-two UNCAPPED 3G — the launder engine · Abbey 3H-all-to-Ready · Hopex pay-hops lift · Assay ±1 · Kiln · Tollhouse −1-for-+3★ · Bonded); the EPHEMERAL event family is two — the Bonded Store (sails away paying each contributing house 2 goods) and the Victualling Yard (the boarding bonus fires twice, then it sails away — v4.6); the Merchants' Exchange cycles one open lading; the Warping Capstan moves an empty hull (v4.6).
- **Everything is earned — and (v4.2) every item prints its OWN wharf fee.** Recipes ← Bruges/bonuses/Scrivener's; buildings ← London/bonuses; specialists ← Bergen/Hiring Post/bonuses; the non-prize channels pay the item's printed fee (chipless buildings free; never a fee to USE a building). The Market sells nothing; goods pay for brews, commissions (the hull's printed 2/1/0 G fee — v4.8), rent and fees.
- **Value lives at the kontore** (the Hall is tabled): the parked die's pips (**Novgorod +2★/die**, v4.2) + tiered majorities (Bruges 4/2/0 · London 5/3/1 · Bergen 9/5/2 · Novgorod 8/5/2) + the bank (Contract ★ · stamps · 1★ bumps · departing marks — builds and commissions bank nothing in play, v4.5b/v4.9) + the standing marks' pips + the Flight (distinct beers SHIPPED — v4.9d). **End clock (v4.5):** the first EMPTY TRAY (every die committed) — the dice alone, 13/player (v4.9b; MAX_ROUND 25 backstop).
- **Terminology (canonical):** *the Wharf* = the whole core area; *stations* = the four action spaces; *slots* = the 8 perimeter spaces; a *line* = two stations + their two slots.

### Simulating / smoke-testing the engine — `playtests/sim.js`
The harness was REWRITTEN for v4.0 (the old bot drove the v3 state machine). Run: `node playtests/sim.js [N]` (default `N=100`; covers 2–4p, prints a per-count summary — rounds/band, trigger split, seat wins, per-player brews/deliveries/bank, delivery split by port). Save each run as `playtests/sim-results-v<KEY>.txt`. **It drives the engine's OWN in-page AI** (`aiStep`) rather than appending a separate bot — one policy to maintain. **Env hooks:** `TIER=` apprentice|journeyman|trader|guildmaster|cellarmaster · **`PERSONAS=1` = the v4 PATHWAYS oracle** (trader seats committed round-robin to the four lanes — majority · lifter · builder · breadth — per-lane win rates reported; the v40 4p read: 25/24.5/29.5/21%, fair 25) · `POOL=n` sweeps the dice pool (THE pace dial — v4.1 cut the sailed clock) · `GUILD_MS`/`CELLAR_MS` lower the MC budgets for bulk. *(`sim-analyze.js` and `ai-tune.js` stay retired — the v4 heuristics carry no weight table.)*

**Strategy — drive the *canonical* engine, never a reimplementation (which would drift from `play.html`).** How it works:
- **Extract** `play.html`'s `<script>` and **append** a heuristic bot + game-runner into the **same lexical scope**, then run the combined source once in a Node `vm` with a stubbed DOM/`localStorage`. *Why append-in-scope:* the engine's `S`, `UI`, `undoStack`, `setupN` are `let`-declared → **not** exposed on the `vm` context, so you can't drive from outside; sharing scope lets the bot reach them and call `freshState`/`endTurn`/etc. directly.
- **Speed:** override `render`/`log`/`save`/`snapshot` to no-ops (they're reassignable function declarations). 1500 games run in ~3 s.
- **The bot navigates the engine's own UI state machine** — it switches on `UI.sub` (`move·line·stops·cell·brew·age·source·convert·reach·alms·goaldraw·wild·load·deploy·benefit·end` — note the literal value is still `cell` in code) and `UI.stage` (`shipdest·place·charter_cask·charter_dest`), calling the **same functions the buttons call** (`doMove`, `chooseLine`, `resolveStop`, `brewPick`, `ageAllot`, `harborLoad`, `loadOnto`, `buyTile`, `buyDisplayUp`, `benefitPick`, `endTurn`…). The bot is **topology-agnostic** (reads `CELLROLE`, not letters) and **occupancy-aware** (subtracts `cellToll` when `OCCUPANCY_TOLL` is defined). Greedy heuristics: work the Wharf, brew the highest affordable recipe, age the cask closest to Ready, deploy Ready casks, ship to the best-value *reachable* destination, build a Cog when ship-less, **earn upgrades by delivering** (no goods-buy — v0.12.3), and **Charter only as a relief valve** (slots jammed / `S.ending` / no hull & can't build).
- **Game-over detection:** loop `botActOnce()` until `S.ending && S.active===S.first && UI.sub==='end'` (gameOver fires inside `endTurn` and leaves `UI.sub==='end'`); a guard counter trips on any runaway.

**What it measures / the bar:** **0 crashes and 0 deadlocks** across 2–4p (the hard gate), rounds & % in the 12–25 band, end-trigger (clock vs `MAX_ROUND` ceiling — should be ~100% clock), winner totals/margins/ties, seat win-rate (first-player fairness), the **upgrade earned-via-ship vs bought split**, charters/game, and winner delivery-by-destination/lean.

**Strategy analysis — `playtests/sim-analyze.js`:** `TIERS=trader node playtests/sim-analyze.js 400` runs headless cohorts and reports **openings → win-rates, timing curves (first voyage/upgrade/Hall/Bergen), per-tier action profiles, destination sequencing, and win correlates**, from a structured event stream hooked on the engine's own functions (`SAVE=1` dumps raw JSONL). `TIERS=guildmaster,trader COUNTS=2` is the *oracle* cohort — what search-based play does differently (~5s/game; size N accordingly). Use it for "how is the game actually played" questions; sim.js stays the robustness gate.

**Bulk-run discipline (standing, ruled 2026-07-12): FAN OUT, never serialize.** Big corpora/ladders are embarrassingly parallel — generate the shard files, launch **every shard at once as parallel background processes** (or subagents), and sync the analysis afterward; do NOT run serial batches that stretch to hours. Oversubscribing the cores squeezes the per-decision MC budgets equally for every seat in a game, so within-corpus comparisons stay fair — note the contention level in the corpus README and keep it uniform across the run. Check progress by counting `pbp-*.log` files, and write analyzers to tolerate a partial corpus so reads can start before the tail lands.

**Re-run checklist after an engine change (designer-ruled 2026-07-13 — LIGHT by default):** (1) bump the `KEY`; (2) `node playtests/verify-v4.js` (seconds — always); (3) **if a sim feels necessary, run 5–10 games TOTAL** (e.g. `node playtests/sim.js 3` covers 2–4p ×3) — crash-free is the bar. **Do NOT run a full battery per change — the designer says when a full validation runs.** When asked, the full v4 gates are: `node playtests/sim.js 500` (commit as `sim-results-v<KEY>.txt`) + `PERSONAS=1 node playtests/sim.js 200` (the PATHWAYS oracle) + `node playtests/ai-ladder.js` (every rung ≥60%, 0 errors — shard the MC rungs: `PAIR=trader,guildmaster` / `PAIR=guildmaster,cellarmaster` with `GUILD_MS=120`/`CELLAR_MS=400` bulk budgets) + `node playtests/ai-render-smoke.js` (full AI games, GM/CM included, through the REAL render layer). `play.html` carries all five in-page **AI seats** (Apprentice/Journeyman/Trader/Guildmaster/Cellarmaster — the v4 rebuild, `AUTOMA.md`; the MC pair clones (S,UI), determinizes the decks, and rolls out with the greedy tiers — ~100 lines).
